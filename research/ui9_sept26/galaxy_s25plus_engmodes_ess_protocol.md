# Galaxy S25+ (SM-S936B) Bootloader EM Token System — Part 4: The AT+ENGMODES Pre-Request Protocol and ESS Encryption Pipeline

*Static analysis — One UI 9 / SM-S936B — November 22, 2026*

*This is Part 4 of the static-analysis series on the SM-S936B / One UI 9 Engineering Mode token system, continuing from Odin.efi/engmode.mbn (Part 1), linuxloader.efi (Part 2), and the `ENGRSS0002` token container format (Part 3). Part 1 already identified the `AT+ENGMODES=0,1,...` pre-request flow and the `EBS Protocol CA` certificate used to protect it in transit. This part goes considerably deeper on that specific mechanism: the exact plaintext layout of the pre-request message, the double-layer encryption pipeline that protects it, the full `AT+ENGMODES` command table, and the strict wire-format validation `engmode.mbn` applies before it will even attempt to process one.*

## Overview and scope

The strings between `0x102085` (file offset) and `0x1027C8` (file offset) in `engmode.mbn` describe the entire format produced by TrustZone when building a pre-request (`em_ess_make_token_request`). Following the cross-references from those strings into the surrounding decompiled functions reconstructs the full **ESS (Engineering Security Service?) pre-request pipeline** end to end: how the plaintext request is assembled, how it is encrypted and packaged for transport, which `AT+ENGMODES` sub-commands exist and what each one does, and the exact wire format `engmode.mbn` demands before it will act on a request.

> **A note on addressing.** This report mixes two different address spaces, as Part 1 also did implicitly. String locations such as `0x102085`–`0x1027C8` above (and `0x102569`/`0x1025D1` below) are **raw file offsets** inside the `.mbn` image itself. Function and data-symbol names such as `FUN_0011a90c` or `DAT_001f4f4d` are **Ghidra virtual addresses (VMA)**, assigned after the ELF segments are mapped — a different, non-identity-mapped address space. As a fixed reference point: VMA `0x102054` is `em_clear_rpmb`, a function with no direct relationship to the pre-request flow — it's cited here purely to show that file offset and VMA diverge quickly and shouldn't be read as interchangeable.

Two binaries are involved, matching the split already established in Parts 1–2: in Download Mode, the Odin LOKE protocol carries this same `esk`/`erm`/digest JSON/Base64 container over the bootloader's UEFI USB-bulk interface (`abl.elf` / `Odin.efi`); once Android has booted, the `engmode` daemon exposes the identical container through the `AT+ENGMODES` AT-command interface. Either way, the payload and its cryptography are built by the same TrustZone code in `engmode.mbn` — only the transport differs.

## Stage 1 — building the plaintext request (`em_ess_make_token_request`, `FUN_0011a90c`)

`FUN_0011a90c` is `em_ess_make_token_request`, with `em_ess_make_token_message` (named from a string at file offset `0x102569`) inlined directly into it. At a high level, this function:

- Generates a random nonce (`"Failed to make nonce"`) and an internal identifier, `iin` (`"Failed to make iin"`).
- Collects the device's model name, IMEI, hardware identifier (`did`), and current ANDROID-mode state (file offset `0x1025D1`).
- Hands the assembled plaintext buffer to `em_ess_encrypt_message` for encryption and packaging (Stage 2, below).

### The 18-field plaintext layout

The plaintext buffer lives at `DAT_0025f270 + 0x94`. Fields are concatenated by a helper at `FUN_0010bb70` — effectively `append_field(dst_buf, &cursor, src, len, delimiter, max_size, max_field_len)` — joined by a delimiter byte stored at `DAT_001f4f4d` (most likely `,` or `|`). Walking `FUN_0011a90c` field by field gives this exact order:

| # | Source | Max size | Field |
|---|---|---|---|
| 1 | `param_1 + 0x1ed18` | 0x200 | "ESS prefix body" (gated by `(uVar12 >> 3) & 1`) |
| 2 | `param_1 + 0x33f1a` (copied from `param_1 + 0x28`) | 0x10 | DID — 16 hex characters of the SoC identifier. Notably tested against `*psVar2 == 0x3034`, i.e. ASCII `"40"` in little-endian — a check for a specific SoC family prefix |
| 3 | `param_1 + 0x33f2a` (copied from `param_1 + 0x38`) | 0x0F | IMEI — 15 digits (gated by `(uVar12 >> 0x14) & 1`) |
| 4 | `param_1 + 0x33ec4` (copied from `param_1 + 0x87`) | 0x10 | Model name, e.g. `SM-S936B` (gated by `(uVar12 >> 0x19) & 1`) |

Field 18 being conditional on the DID prefix is a nice confirmation that this code path branches on SoC generation — older or non-Qualcomm DIDs skip that trailing field entirely.

## Stage 2 — encryption and AT response formatting

### `em_ess_encrypt_message` (`FUN_0011b174`)

Once the 18-field plaintext buffer is assembled, `FUN_0011a90c` calls:

```
iVar6 = FUN_0011b174(lVar7, &local_a0, param_1);
```

This is `em_ess_encrypt_message`, and its decompilation exposes the exact double-layer scheme used to protect the request:

**1. Symmetric encryption of the payload (`erm`)**
- Generates a random AES-256 session key (0x20 bytes, at `DAT_0025f270 + 0x258b4`) and an AES IV (0x10 bytes, at `DAT_0025f270 + 0x258a4`).
- Calls `FUN_00105358` to AES-encrypt the 18-field plaintext buffer (`DAT_0025f270 + 0x94`, `"Failed to encrypt req msg"`) — producing the encrypted `erm` block at `DAT_0025f270 + 0xc898`. This is the encrypted `ENGREQ0200` container.

**2. White-Box protection + RSA encryption of the session key (`esk`)**
- Generates a second IV (`wb iv`, 0x10 bytes at `DAT_0025f270 + 0x258d4`).
- Calls `FUN_00116908` to apply a White-Box transform (`"Failed to encrypt(wb) SS data"`; `uVar14 = 10` specifically when the certificate's Issuer CN is `"EBS Protocol CA"`) over the 0x30-byte block formed by `session_iv + session_key` (at `0x258a4`).
- Calls `FUN_00105838` — `em_crypto_rsa_encrypt` — to RSA-encrypt the `wb_iv` (0x10 bytes) concatenated with the White-Box-protected block, using the public key extracted from the certificate passed in `param_3 + 0x1dd14`. This produces the `esk` block (`DAT_0025f270 + 0x25968`), 256 or 512 bytes depending on whether the certificate carries an RSA-2048 or RSA-4096 key.

So the AES session key is never sent in the clear or RSA-encrypted directly — it first passes through a White-Box-obfuscated transform (keyed to the specific `EBS Protocol CA` issuer) before RSA wraps it. This is an extra layer beyond a plain "AES key + RSA envelope" scheme.

**3. Digest computation and final field assembly**
- Concatenates `esk + erm`, computes their SHA-256 (`FUN_00103630`, `"Failed to make digest of esk_erm"`, at `0x26578`), and hex-encodes the result.
- Assembles the final output as 8 fields:

```
[version (2 bytes)], [esk_len], [esk_b64_len], [esk_hex],
[erm_len], [erm_b64_len], [erm_hex], [sha256_hex]
```

**A naming quirk worth flagging:** despite the `_b64` in `esk_b64_len`/`erm_b64_len`, the actual encoding applied to the raw `esk` buffer (`0x25968`), the raw `erm` buffer (`0xc898`), and the SHA-256 digest (`0x26578`) is **hexadecimal**, not Base64 — all three go through the same hex-encoding routine, `FUN_0010c788`, that Stage 1 uses to turn the 32-byte `nonce` and `iin` into 64 hex characters. The `"esk.data_b64"` / `"erm.data_b64"` label strings passed to `FUN_0010c9c8` appear to be a holdover from an earlier protocol revision that genuinely used Base64 — which Download-Mode Odin's LOKE transport still does — while the current AT v1 transport (`engmode` daemon / `AT+ENGMODES`) encodes `esk` and `erm` as hex under the same old field names.

### Formatting the AT response

Back in `FUN_0011a90c`, after `FUN_0011b174` returns, the AT response buffer (`param_1 + 0x11510`) is built as:

1. The literal `"+ENGMODES:"` (10 bytes).
2. 1 byte read from `param_1 + 0x2ff78`, separated by the delimiter at `DAT_001f4f0f` (`,`).
3. 2 bytes read from `DAT_001fb927`, separated by the same delimiter.
4. The `local_a0` bytes produced by `FUN_0011b174` — the `esk`/`erm`/digest block — appended directly.

This is the exact byte-for-byte construction behind the `esk.data_b64` / `erm.data_b64` pair referenced in Part 1: `esk.data_b64` (`ess_ctx->esk.str_len`) is the RSA/White-Box-wrapped session key, and `erm.data_b64` (`ess_ctx->erm.str_len`) is the AES-encrypted `ENGREQ0200` request container — hex-encoded in this transport despite the inherited `_b64` field name (see the naming note above).

## The full `AT+ENGMODES` command table (`em_ess_command`, `FUN_00118144`)

`FUN_00118144` dispatches on the string following `AT+ENGMODES=`, read as a little-endian 32-bit comparison (`0x2c312c30` = `"0,1,"`, `0x2c322c30` = `"0,2,"`, and so on). This gives the complete command set:

| AT command | Match value | Function | Role |
|---|---|---|---|
| `AT+ENGMODES=0,1,<prefix_body>` | `0x2c312c30` (`"0,1,"`) | `FUN_0011a90c` (`em_ess_make_token_request`) | Builds the pre-request (`esk` + `erm` + digest) from a supplied `prefix_body` |
| `AT+ENGMODES=0,2,<rxiv>,<etoken>` | `0x2c322c30` (`"0,2,"`) | `FUN_0011c8b8` (`em_ess_install_token_v1`) | Installs the encrypted token returned by the Samsung server (requires an active pre-request already in RAM — bit `0x40` of `param_1 + 10`) |
| `AT+ENGMODES=0,0,<...>` | `0x2c302c30` (`"0,0,"`) | `FUN_0011ba28` (`em_ess_make_delete_request`) | Builds a server-side revocation/delete request |
| `AT+ENGMODES=0,3,<...>` | `0x2c332c30` (`"0,3,"`) | `FUN_0011c474` (`em_ess_make_recovery_request`) | Builds an ESI recovery request |
| `AT+ENGMODES=0,4,<...>` | `0x2c342c30` (`"0,4,"`) | `FUN_0011cdf8` (`em_ess_recovery_esi_v1`) | Restores ESI state from the server's response |
| `AT+ENGMODES=0,0,3,0` | literal `"0,0,3,0"` | `FUN_0011d0f0` (`em_ess_delete_token_offline`) | Deletes the token offline, with no server round-trip |
| `AT+ENGMODES=1,1,0` | literal `"1,1,0"` | `FUN_001105a0` | Reads currently active modes, or returns `NO_TOKEN` (`DEL,R1..R4`, `EXP,R1..R2`) |
| `AT+ENGMODES=1,3,1` | direct read | — | Reads the extended SoC ID / DID (`param_1 + 0x352e0`) |
| `AT+ENGMODES=1,2,0` / `2,2,...` | `"1,2,0"` / `0x2c322c32` | `FUN_0011429c` / `FUN_001139dc` | Reads / sets `priority_time` |

One detail worth flagging explicitly: `AT+ENGMODES=0,1,0` — the form you'd naively expect from the command name alone — is **rejected** for having too short an argument. The real pre-request command is `AT+ENGMODES=0,1,<ess_prefix_body>`, where `FUN_0011938c(1, param_1 + 0x11514, bVar9)` parses a structured header (the `prefix_body` plus the `EBS Protocol CA` certificate) that the client-side tool must supply up front.

## Wire-format validation for `AT+ENGMODES=0,1,...` (`em_ess_parse_command_v1`, `FUN_0011938c`)

When `AT+ENGMODES=0,1,<payload>` is received, `param_2` points just past `"0,1,"`, and `engmode.mbn` enforces five strict constraints before it will touch the payload:

1. **Initial version tag** (`*param_2`): the first two characters must be `"01"` (`0x3130`) or `"04"` (`0x3430`).
2. **Separator count** (`iVar9 = 0xb` = 11 for type `1`): the `:`-counting loop starts `iVar7` at `1` and requires `iVar7 == iVar9 + 1` (12) to accept the command — which means the string must contain exactly **11** `:` characters in total (`if (*pcVar18 == ':') iVar7 = iVar7 + 1; if (iVar7 != iVar9 + 1) ...`), confirming `:` as the primary field separator for this command. `FUN_0010c09c` (`strtok`) then splits the string into tokens on that same separator, and the SHA-256 digest is read from `local_130[iVar9 - 1]`, i.e. `params[10]` — the **11th token, at indices `0`–`10`**. Eleven `:` separators producing only 11 non-empty tokens implies either a trailing, empty 12th field after a final `:` (`01:...:cert_len:cert_hex:sha256:`), or simply a mandatory trailing separator the format requires but never populates.
3. **The last three fields are fixed-purpose:**
   - `params[8]` (`lVar20`, max 8 digits): the byte size of the DER-encoded certificate that follows, verified numerically (`FUN_0010b8c0`) and cross-checked against `len(params[9]) / 2`.
   - `params[9]` (`lVar19`, max `0x1000` = 4096 hex characters): the full X.509 certificate, hex-encoded (`FUN_0010b9b8` decodes it to binary at `DAT_0025f220`).
   - `params[10]` (`lVar16`, 0x40 = 64 hex characters): a SHA-256 digest. The digest is computed over `sBodymsg`, derived as `iVar7 = iVar7 + ~uVar6` — i.e. `strlen(param_2) - strlen(params[10]) - 1` — which strips off exactly the 64 digest characters and the single `:` immediately preceding them, leaving everything from `"01:"` up to (but not including) that final `:` as the hashed body.
4. **The `prefix_body`** (stored at `DAT_0025f230`): the intermediate fields `params[1]`–`params[7]`, carrying the request's metadata — license type, operator/session identifier, and the requested mode bitmask.
5. Any violation of the above (wrong version tag, wrong separator count, size mismatch between `params[8]` and `params[9]`, bad digest) aborts parsing before the certificate or payload is used for anything.

So the "prefix_body" referenced throughout Stage 1 is not a single opaque blob — it is itself a `:`-delimited structure with its own fixed positions, and the certificate that accompanies it is supplied by the client on every single pre-request, not cached from a previous exchange.

## RSA-OAEP and certificate-chain validation (`em_crypto_rsa_encrypt`, `FUN_00105838`)

`FUN_00105838` is the function actually called from Stage 2 to RSA-encrypt the White-Box-protected session-key block. Its decompilation settles three points:

- **The supplied certificate is validated before it is trusted.** Before using the public key from the certificate in `params[9]` to encrypt anything, TrustZone calls `FUN_00104d04` to verify that this X.509 certificate chains back to the `CN=EBS Protocol CA` root embedded in `engmode.mbn` (`"Failed to verify cert"`). A self-signed or otherwise unrelated certificate supplied in the AT command is rejected at this step — it is not enough to simply hand `engmode.mbn` *any* certificate and have it encrypt the session key against it.
- **The padding scheme is RSA-OAEP, not PKCS#1 v1.5.** The call `FUN_001a4550(..., 4)` — where the literal `4` selects the padding mode, and the corresponding failure string reads `"No OAEP support(%s)"` — confirms that `esk` is RSA-encrypted using OAEP padding. This is a different scheme from the raw PKCS#1 v1.5 padding documented in Part 3 for the `ENGRSS0002` token's own `INTE` signature; the two use the RSA primitive for different purposes (signing vs. encryption) and, as it turns out, different padding conventions as well.
- **Why `AT+ENGMODES=0,1,...` is normally blocked by PACM (`NOT_ALLOWED_SLO`).** As `FUN_0011938c`'s strict parsing requirements make clear, this is not a command meant to be typed in by hand. In the real flow, a Samsung-side tool (the Android `ServiceMode`/`FactoryTest` app, or the PC-side EBS Client tool) first builds the header — `01:...:<cert_len>:<cert_hex>:<sha256>` — sends it as the `AT+ENGMODES=0,1,...` command, receives back the `+ENGMODES:0,1,<esk>,<erm>,<sha256>` blob that `engmode.mbn` generates in response, forwards that blob to Samsung's EBS server, and then feeds the server's answer back into the device via `AT+ENGMODES=0,2,<rxiv>,<etoken>` — the command that actually installs the resulting token (handled by `em_ess_install_token_v1`, `FUN_0011c8b8`, as noted in the command table above).

## Summary

| Stage | Function | What it does |
|---|---|---|
| Plaintext assembly | `FUN_0011a90c` (`em_ess_make_token_request`) | Builds the 18-field request buffer: DID, IMEI, model, nonce, `iin`, platform flag, `"ANDROID"`, and several context/state fields |
| Symmetric encryption | `FUN_00105358` (via `FUN_0011b174`) | AES-encrypts the plaintext buffer into `erm` |
| Key protection | `FUN_00116908` (via `FUN_0011b174`) | White-Box-transforms the AES session key + IV, keyed to the `EBS Protocol CA` issuer |
| Asymmetric key wrap | `FUN_00105838` (`em_crypto_rsa_encrypt`) | Validates the supplied certificate against the `EBS Protocol CA` root, then RSA-OAEP-encrypts the White-Box-protected key block into `esk` |
| Digest + assembly | `FUN_00103630` / `FUN_0010c788` (via `FUN_0011b174`) | SHA-256 over `esk + erm`, hex-encoded, packaged into the final 8-field `esk`/`erm`/digest response |
| Command dispatch | `FUN_00118144` (`em_ess_command`) | Routes every `AT+ENGMODES=<a>,<b>,...` variant to its handler |
| Wire-format validation | `FUN_0011938c` (`em_ess_parse_command_v1`) | Enforces the 11-separator, `:`-delimited structure of `AT+ENGMODES=0,1,...` (tokens at indices `0`–`10`), including the certificate-length/digest cross-checks |

*As with the rest of this series, this reflects one firmware/server generation of `engmode.mbn`; exact field counts, offsets and command IDs may shift across revisions.*
